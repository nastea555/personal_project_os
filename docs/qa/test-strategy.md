# Test Strategy — Personal Life Hub

Версия: 0.1 · Статус: черновик на ревью · Дата: 2026-10-27

## 1. Цели

- Подтвердить, что каждый критерий приёмки (AC) выполнен и проверен хотя бы одним тест-кейсом (TC).
- Защитить детерминированные бизнес-правила (расчёт калорий, валидация, неизменность истории) от регрессий.
- Гарантировать сохранность данных (persistence) и честный UI (нет фиктивных данных и нерабочих кнопок).

## 2. Подход: Hybrid QA

Автоматизация там, где проверка повторяемая и объективная; ручная проверка — там, где важна оценка человеком (визуальная целостность, удобство на телефоне, тексты пустых состояний). Каждый TC помечен способом выполнения: `auto` / `manual` / `auto+manual`.

## 3. Уровни тестирования

| Уровень | Что проверяем | Инструменты | Где лежит |
|---|---|---|---|
| Unit (backend) | Расчёты, валидация, сервисы | JUnit 5, AssertJ | `backend/src/test` |
| API | Контракты, коды ответов, Problem Details | Spring Boot Test + MockMvc | `backend/src/test` |
| Integration (БД) | Миграции Flyway, репозитории, транзакции | Testcontainers (PostgreSQL 16) | `backend/src/test` |
| Component (frontend) | Компоненты, состояния, формы | Vitest + React Testing Library | `frontend/src/**/*.test.tsx` |
| UI / E2E | Пользовательские сценарии, маршруты, адаптивность | Playwright | `tests/ui`, `tests/e2e` |
| Accessibility | Нарушения WCAG 2.1 AA | @axe-core/playwright + ручная клавиатурная проверка | `tests/ui` |
| Manual exploratory | Визуал, UX на реальном телефоне | Чек-листы в спецификациях | — |

Пирамида: больше всего unit/component, меньше — E2E. E2E покрывают ключевые сценарии, а не каждую ветку.

## 4. Типы проверок (чек-лист для каждой функции)

positive · negative · boundary values · validation · error handling · persistence · integration · responsive UI · accessibility · regression.

## 5. Окружения и вьюпорты

| Профиль | Размер (px) | Назначение |
|---|---|---|
| Desktop L | 1440×900 | Основной компьютер |
| Desktop S | 1024×768 | Граница перехода layout |
| Tablet | 768×1024 | Промежуточный |
| Mobile | 390×844 | Основной телефон |
| Mobile S | 320×568 | Минимальная ширина |

Браузеры в Playwright: Chromium (обязательно), WebKit (мобильный Safari — обязательно для мобильных сценариев), Firefox (по возможности в CI).

## 6. Тестовые данные

- Только синтетические данные; никаких реальных персональных данных в фикстурах.
- Backend-интеграционные тесты: чистая БД на каждый класс тестов (Testcontainers) + данные через API или SQL-фикстуры.
- E2E: БД сбрасывается перед прогоном; данные создаются через API, а не через UI (быстрее и стабильнее), кроме сценариев, где проверяется сам UI-ввод.

## 7. Правила для тестов

- Тест проверяет наблюдаемый результат и бизнес-правило, а не повторяет реализацию.
- Нет тестов, которые проходят безусловно; новый тест сначала должен упасть на заведомо неверном поведении (проверка «красный → зелёный»).
- Локаторы в UI-тестах — по роли и доступному имени (`getByRole`), `data-testid` — только когда роли недостаточно.
- Никаких `sleep`; ожидание — через web-first assertions Playwright.
- Тесты не отключаются ради зелёной сборки. Нестабильный тест — дефект с владельцем и сроком.

## 8. Entry / Exit criteria

**Entry (начало реализации функции):** спецификация прошла QA-ревью, замечания уровня High закрыты; AC и TC имеют ID; открытые вопросы закрыты или зафиксировано предположение.

**Exit (Definition of Done):**
- все AC покрыты TC, матрица трассируемости обновлена;
- автотесты реально запущены, результат приложен к отчёту (команда + вывод);
- ручные TC выполнены, результат записан;
- нет открытых дефектов Critical/High;
- проверено на Desktop L и Mobile как минимум;
- ограничения и непокрытые риски перечислены.

## 9. Классификация дефектов

| Severity | Пример |
|---|---|
| Critical | Потеря/искажение данных, неверный расчёт калорий, приложение не запускается |
| High | Основной сценарий недоступен, нет обходного пути |
| Medium | Сценарий работает с обходным путём; нарушение доступности |
| Low | Косметика, тексты |

## 10. CI (GitHub Actions)

На каждый push/PR: lint + typecheck + unit/component (frontend), unit + API + integration (backend, Testcontainers), сборка, Playwright (Chromium + WebKit) против собранного приложения. Отчёт Playwright — артефакт сборки.

## 11. Отчётность

После каждого этапа — отчёт: что создано, команды запуска, какие тесты реально запущены (с результатом), какие не запускались и почему, известные дефекты и риски.

## 12. Риски

| Риск | Митигация |
|---|---|
| Сборка невозможна в текущей песочнице (ADR-009) | Решение владельца по окружению до начала реализации |
| Web Speech API не поддерживается частью браузеров | Fallback на текстовый ввод; отдельные TC в F-VOICE-001 |
| Нестабильность E2E | Данные через API, web-first assertions, повтор только в CI с фиксацией |
| Расхождение спецификации и кода | Матрица трассируемости обновляется в том же изменении, что и код |
